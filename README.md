# 校园校服订购尺码试穿与售后换码平台

面向学校多校区校服统一采购的全流程协同平台。**学校总务、班主任、家长、供应商、工厂、售后客服** 围绕
**同一名学生、同一批校服**协同处理：订购计划维护 → 家长填报尺码 → 试穿日登记五类尺码建议 →
家长确认/缴费（贫困生减免）→ **集中试穿漏测补测与生产锁定（候选时段/样衣竞争/双确认/预锁延后）** →
班级汇总 → 工厂生产批次 → 供应商分批发货 → 学校分批发放签收 →
换码/补发/退款/投诉 → 供应商考核归档。

技术栈：**Next.js 14（App Router + Route Handlers，React 全栈）+ TypeScript + MySQL 8 + mysql2**，
一键启动：**Docker Compose**（MySQL + App 两个容器，首次启动自动建表并写入演示数据）。

---

## 一、一键启动（推荐，需本机有 Docker）

```bash
docker compose up --build
```

- 应用：<http://localhost:3000> （首次启动自动建表 + 灌入演示数据）
- MySQL：`localhost:3306`，库名 `uniform`，root 密码 `uniform_pwd`
- 停止并清空数据：`docker compose down -v`
- 不想自动灌入演示数据：把 `docker-compose.yml` 中 `SEED_DB: "1"` 改为 `"0"`

## 二、本地开发启动（不用 Docker 时）

前置：Node.js 20+、可访问的 MySQL 8/MariaDB 10.11+。

```bash
npm install
# 1) 建库建表（自动 CREATE DATABASE uniform，并执行 db/schema.sql）
npm run init-db
# 2) 灌入演示数据（可选；重复执行会先清空再写入）
npm run seed
# 3) 开发模式启动
npm run dev
# 或生产模式：npm run build && npm run start
```

数据库连接通过环境变量配置，默认值见 `.env.example`：

```bash
DB_HOST=127.0.0.1 DB_PORT=3306 DB_USER=root DB_PASSWORD= DB_NAME=uniform
```

## 四、功能与页面

登录后按角色显示菜单：

1. **进度看板 `/dashboard`**：按学生/班级汇总缴费、试穿、投产、签收、未闭环售后。
2. **订购计划 `/plans`**：总务维护年级/班级、季节套装/运动服/礼服/增购件五类品类；
   支持**多校区统一采购**（勾选多校区）与**毕业班补订**（`kind=makeup`）；家长下单时
   **自动带入试穿日工作人员的尺码建议**。
3. **学生与尺码 `/students`**：家长填写身高体重、常穿尺码、特殊版型；转学处理；贫困生减免申请与审批。
4. **试穿日 `/fitting`**：班主任按时段组织；工作人员逐人登记**上衣、裤子、裙装、外套、鞋码**五项建议。
5. **订单缴费 `/orders`**：草稿 → 家长确认 → 缴费；总务可挂起（迟缴费/转学等）、解除、取消；
   订单详情展示该生**全过程时间线**与每件校服的批次/发货/签收/售后链路。
6. **生产批次 `/batches`**：供应商/工厂按「品类+尺码+数量」建批次，系统按缴费先后 **FIFO 自动分配到学生**；
   只有**已缴费且在校**学生的订单可投产，数量不足会明确报出差额；支持开工/报产/预计到校维护。
7. **投产限制 `/production-blockers`**：供应商明确看到**哪些订单不能进入生产及原因**
   （家长未确认、未缴费、订单挂起、学生转学、已取消）。
8. **分批发货 `/shipments`**：一个批次可分多批发货；总务逐件确认实际到校数，
   **少于发货数即工厂漏发**，自动写入学生时间线并引导补发工单。
9. **分批发放 `/distributions`**：按班级安排多个常规发放场与**补领场**（缓解换码高峰/发放拥堵）；
   支持正常签收、**缺件登记、班级错领登记（记录错领人）**，异常补发完成后自动闭环。
10. **售后工单 `/cases`**：换码（成长过快/试穿偏差）、补发（工厂漏发/错领）、退款（转学/迟缴取消/过敏）、
    面料过敏投诉、转学取消；售后客服分派，供应商/工厂在同一工单上推进；
    换码完成后订单明细尺码同步更新。
11. **供应商考核 `/assessments`**：按计划自动统计漏发数、延期数、过敏投诉数、换码数并评分留档。
12. **集中补测与生产锁定 `/makeup`**：集中试穿日多名学生请假漏测后的补测闭环（详见下节）。

### 集中试穿漏测：补测与生产锁定（`/makeup`）

- **漏测登记与风险占位**：系统按「有本计划有效订单但无任何试穿记录」识别漏测学生；补测前家长只能提交
  **参考尺码**，订单标记为 **风险占位（placeholder）**，供应商生产计划可见但**不计入正式数量、不能投产**。
- **候选时段生成**：总务/班主任按班级生成候选，输入为**班级、校区、供应商可用尺码样衣、班主任空闲时间**。
- **多班竞争与优先级**：多个班竞争同一批样衣或同一时段时，按 **① 距班级生产截止日远近 → ② 首次订购人数 →
  ③ 班级已确认人数** 计算优先级并展示竞争班级；样衣不足的候选明确标出差额且不能确认；人工调整补测场
  **必须填写原因**并留痕。
- **两次确认**：补测后**班主任先确认测量记录，家长再确认最终尺码**；两者一致才正式锁定；不一致订单进入
  **待复核（review）**，供应商不能锁定生产，由总务裁决（采用教师/采用家长/退回重测）。
- **截止日处置**：到班级生产截止日仍未闭环，总务可**按参考尺码预锁**或**延后该学生**；系统同步
  **重算班级数量、生产批次（延后退出已分配批次）、到校承诺**，选择与影响写入学生订单与 `makeup_decisions`。
- **可追溯异常台账**：补测逾期、样衣不足、班主任超时未确认、家长超时未确认、截止日未闭环、两次确认不一致
  六类异常自动登记（系统幂等扫描），支持「知晓 / 解决」全程留痕。
- **供应商风险看板**：按品类+尺码分列「正式可生产 / 风险占位 / 预锁 / 待复核 / 延后」数量。
- 首次订购判定：该生在其他计划中无有效订单即为首次订购（演示中罗小宇有历史订单 → 非首购）。

## 六、数据库结构

`db/schema.sql`，36 张表，核心：

- 组织：`campuses / grades / classes / users / students / suppliers / subsidies`
- 计划：`plans / plan_campuses / plan_grades / plan_items`
- 试穿：`fitting_sessions(kind=regular/makeup) / fitting_records`
- 订单：`orders(status 含 review, production_lock) / order_items`
- 生产：`production_batches / batch_items / batch_allocations`
- 物流：`shipments / shipment_lines`
- 发放：`distributions / receipts`
- 售后：`aftersales_cases / exchange_requests / resend_records / refund_records / supplier_assessments`
- 集中补测：`teacher_slots（班主任空闲）/ sample_stocks（样衣库存）/ sample_reservations（样衣占用）/
  class_production_settings（班级生产截止日与到校承诺）/ makeup_sessions（补测候选/场次，含优先级与人工调整原因）/
  makeup_students（参考尺码→教师测量→家长最终确认/待复核/预锁/延后）/ makeup_exceptions（六类可追溯异常）/
  makeup_decisions（总务预锁/延后/复核裁决及重算影响）`
- 协同留痕：`activity_log`（所有角色围绕同一学生/订单的动作时间线）
